"Agent swarm" is the phrase of the month. I had read about swarms. I had not run one. This Post is the technical record of my first run: how the agents were started, how a message gets from one to the other, what each agent cost, and what the log looks like when agents write it by hand.

## The job

A sweep of my home network had found ten live addresses with no record. The job: say what each device is, with evidence.

It is a good first job for three reasons. It ends. Each claim can be checked against a real device. And it splits into parts that need different habits: gather, decide, doubt.

## What ran where

| Part | Model | Where |
| --- | --- | --- |
| Main session | Claude Opus 5.5 | Claude Code on my laptop |
| Clotho, gathers | Claude Opus 5.5 | Background subagent of that session |
| Lachesis, decides | Claude Opus 5.5 | Background subagent of that session |
| Atropos, reviews | Claude Opus 5.5 | Background subagent of that session |
| Local models | None | Not used in this run |

I checked the model of each subagent in its transcript after the run. All three ran on the same model as the main session.

The cloud was a choice. One 16 GB card serves one large model at a time, and each agent in this run read tens of thousands of tokens. For a first proof I wanted to learn about the swarm and not about a queue. The agents also ran on the laptop and not in sandbox VMs, because the job was to look at my home network and the sandbox blocks exactly that.

## How a message gets from one agent to the other

I had the wrong picture of an inbox. I expected a mailbox that each agent checks. Claude Code works in a different way, and the difference shapes the whole design.

- A subagent starts as a background task and gets an id.
- An agent sends with one tool call: a receiver and a text.
- If the receiver is in the middle of its work, the message arrives at its next tool call.
- **If the receiver has stopped, the message starts it again, with its full earlier context.**

So no agent polls, and no agent sleeps in a loop. An agent that has nothing to do ends its turn.

A subagent has an id and no name, and the id exists only after the start. So the agents could not know each other's address from their prompt. The main session started all three, then wrote one file:

```json
{
  "clotho": "aef9…",
  "lachesis": "a6c7…",
  "atropos": "a33d…",
  "main": "main"
}
```

Each agent read that file at the moment it had to send. After it was written, the main session passed no message. It only received a report each time an agent stopped.

Two of the three agents had nothing to do at the start. Their prompt said: read the shared brief, load the message tool, answer "ready", and stop. The first message from Clotho woke Lachesis. The first message from Lachesis woke Atropos.

## The brief

All three agents read one shared file before their own instructions. Three parts of it carried the design.

**One owner for each file.** No shared writes.

| File | Owner | Content |
| --- | --- | --- |
| `evidence.md` | Clotho | Raw facts for each address, each with the command that gave it |
| `identities.md` | Lachesis | One row for each address: device, confidence, evidence used |
| `final.md` | Atropos | The accepted list, the open list, and the reasons |
| `messages.log` | All | One line for each message sent, received, or acted on |

An agent that disagrees with a file cannot edit it. It must send a message, and the message is then the record.

**Hard limits on messages.** At most four sent messages for each agent. No greetings, no thanks, no status reports. A message only when the receiver must do or change something.

**Hard limits on the network.** Only Clotho may probe, and only like this:

```
- Look only. Do not log in to any device, do not guess passwords, do not change
  any setting on any device, and do not send a command to a device.
- Permitted probes: ping, the ARP table, mDNS and DNS-SD browse, reverse DNS, an
  HTTP GET of a front page or a well-known description file, and a TCP connect
  test on this port list only: 22, 53, 80, 443, 445, 548, 554, 631, 1400, 1883,
  3689, 5000, 5353, 7000, 8008, 8009, 8080, 8443, 9100, 32400, 49152, 62078.
- No nmap, no install of any tool, no scan of a different network.
```

A confidence rule for Lachesis did real work later: "high" needs two independent facts that agree, and one fact alone is "medium" at most.

## How Clotho gathered evidence

No scan tool was installed. These were enough:

```sh
# Who is there
for i in $(seq 1 254); do (ping -c1 -t1 192.168.1.$i >/dev/null 2>&1 &); done; sleep 4; arp -an

# Who made the network chip: the first three bytes against the IEEE list
grep -i "^EC-B5-FA" oui.txt

# What a device says about itself
dns-sd -B _services._dns-sd._udp local.        # service types on mDNS
curl -s http://<ip>:8008/setup/eureka_info      # Google cast devices
curl -s http://<ip>/description.xml             # UPnP devices
```

The best single source was a page on the ISP gateway. Its device list answers a plain GET with no login, and gives a name, a hardware address, the link type, and the last activity for each client. For one device it also showed the DHCP client string, `dhcpcd-5.2.12:Linux-5.10.160:aarch64`, which says "embedded Linux on ARM" with no probe of the device at all.

Clotho also wrote down a trap in that page. The gateway lists Wi-Fi clients of a second access point as wired, because that access point hangs on a wired port. A "wired" label there proves nothing.

## The five messages

| Time | From | To | Message | What the receiver did |
| --- | --- | --- | --- | --- |
| 15:51:05 | Clotho | Lachesis | The evidence is ready, and it is thin for five addresses | Made draft decisions |
| 15:51:38 | Lachesis | Clotho | Send the gateway rows for those five | Made one GET of the gateway page |
| 15:52:40 | Clotho | Lachesis | The facts are in the file | Moved one address from low to medium, one from medium to high |
| 15:53:48 | Lachesis | Atropos | The list is ready: 6 high, 2 medium, 2 low | Checked ten rows, rejected three |
| 15:54:48 | Atropos | Lachesis | Three rows are rejected, with reasons | Downgraded one, reworded two |

The second message is where this stops being a pipeline. Lachesis did not accept thin evidence. It asked for one specific fact, from the one agent that was permitted to get it.

## The rejection

One device gave the network a host name that starts with "Restore2". Lachesis wrote it down as a Hatch Restore 2, a bedside sound machine, with medium confidence. Atropos sent this:

```
atropos -> lachesis | REJECT 3 rows: .220 medium rests on the gateway only,
.218 maker Hatch has no fact, .91 'the model with Matter' names one model
without a fact. Change or give a second fact
```

"Maker Hatch has no fact." No probe had returned that word. It came from what the model knows about the world, and it sat in a table next to measured facts with the same weight. Atropos did not say that the guess was wrong. It said that it had no evidence, which is the better complaint.

Before it wrote that message, Atropos had also looked up each of the ten hardware address prefixes in the IEEE list by itself, and had not trusted the vendor column of the other agent.

The second Post in this Series is about a voice assistant that said a light had lost its color, when it could not see color at all. It is the same fault: a gap filled with something that sounds right. There I found it in the logs, after the fact. Here a second agent found it before I saw the result.

## What it cost

| Agent | Tokens | Tool calls | Active time |
| --- | --- | --- | --- |
| Clotho | 100,752 | 21 | 463 s |
| Lachesis | 70,212 | 16 | 252 s |
| Atropos | 72,940 | 10 | 147 s |
| Total | 243,904 | 47 | About 12 minutes of wall clock |

One number stands out. The two agents that only read the brief and stopped used about 46,000 tokens each for that first turn. An agent that waits is not free at the start. It pays for its own context once.

## The raw log, and why I do not trust it

I told each agent to add a line to a shared log with a shell command, for each message sent, received, or acted on. Here is the start of that log, exactly as written:

```
15:51:05 | clotho -> lachesis | evidence.md is ready; thin evidence on .85 .193 .218 .220 .66; .220 is gone
15:51:09 | clotho -> lachesis | RECEIVED evidence.md complete; strong on .83 .84 .88 .209 .91, thin on .85 .193 .218 .220 .66
15:51:38 | lachesis -> clotho | REQUEST gateway device list rows (no login) for .220 .85 .193 .218 .66: hardware address, name, link type, last seen
15:51:48 | lachesis -> clotho | asks for one GET of the gateway device list page, facts for .220 .85 .193 .218 .66
15:52:40 | clotho -> clotho | ACTED on lachesis request: one GET of gateway devices.ha (no login asked); added section 'Added after request from lachesis' to evidence.md
```

Read the second line. Lachesis wrote it on receipt, and kept the direction of the sender. The fourth line is the same message as the third, logged a second time by the receiver. The fifth has the same agent as sender and receiver. Each agent followed the format, and each one read it a little differently.

A log that agents write about themselves is a log you cannot fully trust.

## What did not work well

- **It was a pipeline with two loops.** Nothing ran in parallel. The request for evidence and the rejection are what made it more than a script.
- **A message has no proof of its sender.** It says "From lachesis" because the agent typed it.
- **Ids, not names.** The roster file worked, and it is a workaround.
- **Nine reports for one job.** Each stop of an agent sends a report to the main session.
- **One model in each seat.** Three agents with the same model share the same blind spots. The reviewer worked because of its instructions, not because it was a different mind.

## What I built next

Each fault above became a requirement for a small inbox service of my own, named Hermes:

- The transport writes the log, not the agents.
- Each agent has a token, and the service sets the sender from it.
- Each record has an id, a time, a sender, a receiver, and the id of the message it answers.
- "I acted on this message" is its own record type that must point at a message sent to the caller.
- Names exist before the start.
- A web page shows the records as they arrive.

I built it the same evening and ran three local agents through it, with no cloud model. That is the next Post.

## What I take from this

- **A swarm is roles, files, and messages.** The model was the same in each seat. The difference was what each agent was told to care about and what it was permitted to touch.
- **Give one agent the job of doubt.** The reviewer did not gather and did not decide. It found the one invented fact.
- **One owner for each file.** A disagreement then has to become a message.
- **Set hard limits before the start.** A probe list, look and do not touch, four messages each. The agents used two, three, and one.
- **Start with checkable facts.** I could compare the result with my own home.
- **It costs more than one agent.** For a job this small, one agent can do it for less. The swarm earned its cost in one place: the review.
